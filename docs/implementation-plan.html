Technical plan · pre-implementation

Media Optimizer for Jellyfin

An in-interface file analyser and FFmpeg conversion engine, built as a server plugin. The encoding half is straightforward and safe to build. The in-player UI half has no supported extension point in Jellyfin and must be grafted onto the web client's private DOM — this document is mostly about being precise on which half is which.

target Jellyfin 10.11.x runtime .NET 8.0 licence GPLv3 (forced) encoder jellyfin-ffmpeg status plan only — no code written

Clean to build

  • Server plugin, DI services, custom REST endpoints, admin config page
  • Full file analysis — every field you listed is already in Jellyfin's model or ffprobe
  • Persistent job queue, background worker, progress reporting, cancellation
  • All preset and custom conversion options via FFmpeg
  • Genuinely lossless strategies, with bit-exactness provable by hash
  • Safe output policies: sidecar, alternate version, verified replace with revert

Works, but unsupported

  • The 3-dot menu item and the player button — DOM injection, no official API
  • Delivery depends on the third-party File Transformation plugin, or on patching index.html on disk
  • Selectors are private and did move between 10.11.0 and current master — expect per-release fixes
  • HDR10 survives a re-encode only if metadata is re-injected by hand
  • No way to coordinate CPU/GPU use with Jellyfin's own live transcoder

Not possible

  • Any UI on native clients — Android TV, Roku, Kodi, Swiftfin, the Android app's native player
  • Lossless shrinking of an already-lossy video stream. No tool does this; the UI must refuse it
  • Preserving Dolby Vision RPU through an FFmpeg re-encode
  • One plugin binary across Jellyfin minor versions — ABI is pinned
  • Replacing files in place on read-only or network-mounted libraries

01Findings

What the research actually says

Two separate systems are in play, and they have opposite maturity levels. Getting this distinction right is the whole basis of the plan.

The server plugin API is a real, supported API

Jellyfin plugins are .NET 8/9 assemblies loaded into the server process with full access to the dependency injection container. A plugin can register hosted services, expose its own ASP.NET Core controllers on the main API surface, add scheduled tasks visible in the dashboard, and read or write library items. Everything on the conversion side of this feature lives here and is well-supported.

The web client has no plugin API at all

This is the finding that shapes the design. jellyfin-web is a webpack bundle; its modules are not exposed on window. The 3-dot menu is built in src/components/itemContextMenu.js by pushing entries onto a hard-coded commands array inside getCommands(), and the module's only export surface is { getCommands, show } — reachable from other bundled modules, not from an injected script. There is no registry, no hook, no event to subscribe to.

So the only way to add the menu item and the player button is to observe the DOM and insert elements into markup the Jellyfin team considers private. That works — several popular plugins do exactly this — but it is unsupported by definition.

Churn evidenceBetween the v10.11.0 tag and current master, src/components/actionSheet/actionSheet.js became .ts, and the video OSD moved out of src/controllers/playback/video/ entirely. Both are files this plugin's UI depends on. Treat the selector layer as something you re-verify every Jellyfin minor release, not something you write once.

Script delivery has one good option and one bad one

The plugin needs a <script> tag in the served index.html. The clean route is IAmParadox27/jellyfin-plugin-file-transformation, which intercepts web files as they are served and hands them to registered callbacks. Its current contract (v2.2.x) is a POST:

POST /FileTransformation/RegisterTransformation
{ "id": "<plugin guid>",
  "fileNamePattern": "index.html",
  "transformationEndpoint": "/MediaOptimizer/Transform" }

with an in-process alternative via its IWebFileTransformationWriteService.AddTransformation(Guid, string, TransformFile). The fallback route — editing jellyfin-web/index.html on disk — is destructive, is undone by every server update, and fails outright in read-only or rootless containers. Support it as a last resort with a loud warning; do not make it the default.

02Architecture

Architecture

One assembly, Jellyfin.Plugin.MediaOptimizer, with a strict internal split: an encoding core that has no idea a UI exists, and a web graft that is pure delivery. If the graft breaks on a Jellyfin update, the core keeps working and the feature degrades to the dashboard page rather than dying.

04Interface

The UI, and why it is a graft

Three entry points, all created by observing the DOM. client.js waits for window.ApiClient, then runs a single MutationObserver on document.body with a debounce, matching on the containers below.

Entry point 1 — the 3-dot / right-click menu

Jellyfin renders it as a dialog with class actionSheet containing .actionSheetScroller. Append a button matching the surrounding markup exactly, and it inherits every theme in the ecosystem for free:

<button is="emby-button" type="button"
        class="listItem listItem-button actionSheetMenuItem"
        data-id="mediaoptimizer">
  <span class="actionsheetMenuItemIcon listItemIcon listItemIcon-transparent
               material-icons tune" aria-hidden="true"></span>
  <div class="listItemBody actionsheetListItemBody">
    <div class="listItemBodyText actionSheetItemText">Optimize file…</div>
  </div>
</button>

The item id has to be recovered from the element the sheet was opened against — read data-id from the nearest [data-id] ancestor of the click target and cache it on pointerdown, because the sheet itself does not carry it.

Entry point 2 — the player button

The OSD bar is .videoOsdBottom .buttons. Insert before .btnVideoOsdSettings so it lands next to Settings rather than at the end of the row:

<button is="paper-icon-button-light" class="btnMediaOptimizer autoSize" title="Optimize file">
  <span class="largePaperIconButton material-icons tune" aria-hidden="true"></span>
</button>
Detailis="paper-icon-button-light" is a customised built-in element, so it only upgrades when the parser creates it. Use insertAdjacentHTML, not createElement + className. If the custom element is undefined in a future version, a plain <button> carrying the same classes still renders correctly — degrade to that rather than throwing.

Entry point 3 — the dashboard page

A standard IHasWebPages config page holds global settings and the full queue view. This is the supported surface and the fallback: if injection fails entirely, the plugin is still fully usable from here. Say so in the plugin description.

The dialog itself

Rendered by the plugin, not by Jellyfin, into a full-screen overlay. Styling reuses Jellyfin's own CSS custom properties so user themes carry through, with everything else namespaced .mopt-* to avoid colliding with the host stylesheet. Two panes:

Left — current file
  • Container, file size, duration, overall bitrate
  • Video: codec + profile + level, resolution, bit depth, frame rate (and VFR flag), pixel format
  • Range: SDR / HDR10 / HLG / HDR10+ / Dolby Vision, with profile
  • Every audio track: codec, channels, layout, sample rate, bitrate, language, default flag
  • Subtitle and attachment inventory with per-stream sizes
  • Path, and whether the file sits on writable storage
Right — target
  • Strategy chips: Balanced · Maximum compression · Archive · Lossless only · Custom
  • Resolution: 720p / 1080p / 1440p / 4K / Original / Custom, always aspect-locked and never upscaling
  • Codec, bit depth, CRF-or-bitrate, encoder preset, HW toggle
  • Per-track audio: keep / re-encode / drop, with codec and bitrate
  • Subtitles, chapters, attachments: keep or drop
  • Output policy and the destructive-action confirmation

A persistent estimate bar sits at the foot: predicted size, delta against current, predicted runtime, and any warnings the planner raised — recomputed on every change via /Estimate.

Client coverageThis UI exists in browsers, in Jellyfin Media Player on desktop (which embeds the same web client), and in the Android app's web-view surfaces. It does not exist on Android TV, Roku, Kodi, tvOS, Swiftfin, or in the Android app's native ExoPlayer view — those are separate native codebases a server plugin cannot reach. On those clients the feature is dashboard-only, and there is no workaround short of writing each client yourself.
05Analysis

Reading the current file

Every field requested maps to something Jellyfin already models. Source of truth is a fresh IMediaEncoder.GetMediaInfo() probe — the library's cached values can be stale or incomplete — falling back to the cached MediaSourceInfo if the probe fails.

Panel fieldSourceReliability
File sizeMediaSourceInfo.Sizeexact
ResolutionMediaStream.Width / .Heightexact
Video codec.Codec, .Profile, .Levelexact
Bit depth.BitDepth (or derive from .PixelFormat)exact
Audio codec.Codec, .Channels, .ChannelLayout, .SampleRateexact
Frame rate.RealFrameRate / .AverageFrameRateflag VFR when they differ
HDR / SDR.VideoRange, .VideoRangeType, .ColorTransferexact
ContainerMediaSourceInfo.Containerexact
Bitrate (per stream)MediaStream.BitRateoften absent in MKV
The bitrate problemMatroska frequently carries no per-stream bitrate tag, so MediaStream.BitRate comes back null on a large share of real libraries. Three-tier fallback: (1) the tag if present; (2) subtract known audio/subtitle bitrates from Size × 8 / Duration to derive video bitrate; (3) on demand, an exact count via ffprobe -select_streams v:0 -show_entries packet=size, which is accurate but reads the whole file — offer it as a "measure precisely" button, never on dialog open. Any derived figure renders with a ≈ so the number is never misrepresented as measured.
06Encoding

Planner and FFmpeg workflow

Build your own argument vector

Jellyfin's EncodingHelper is tempting and wrong for this. It is built around EncodingJobInfo for live streaming sessions — HLS segmenting, client device profiles, throttling, seek handling. Archival re-encoding shares almost none of that. Use IMediaEncoder for the binary paths and capability queries, and construct arguments directly as a string[] (never a concatenated shell string — paths contain quotes, spaces and Unicode).

Capabilities are discovered, never assumed

At startup, run ffmpeg -hide_banner -encoders and -filters once and cache the result alongside SupportsEncoder() checks. The UI then only offers what this server's build can actually do. jellyfin-ffmpeg builds vary by platform and distribution; hard-coding libsvtav1 or hevc_vaapi availability guarantees failures on someone's machine.

Representative command

ffmpeg -nostdin -hide_banner -loglevel error -progress pipe:1 -nostats \
  -i INPUT \
  -map 0:v:0 -map 0:a:0 -map 0:s? -map 0:t? \
  -c:v libx265 -crf 24 -preset medium -pix_fmt yuv420p10le \
  -vf scale=-2:1080:flags=lanczos \
  -fps_mode passthrough \
  -x265-params "hdr10=1:repeat-headers=1:master-display=...:max-cll=..." \
  -color_primaries bt2020 -color_trc smpte2084 -colorspace bt2020nc \
  -c:a:0 libopus -b:a:0 256k -ac 6 \
  -c:s copy -c:t copy -map_metadata 0 -map_chapters 0 \
  -movflags +faststart \
  TEMP_OUTPUT

Points that matter

  • Scaling uses -2 on the free axis to keep aspect and stay mod-2. Never upscale — clamp the target to the source and tell the user why.
  • Frame rate defaults to -fps_mode passthrough. Forcing CFR on VFR content is a classic way to desync audio an hour in.
  • Quality defaults to CRF/CQ, seeded from the server's own H264Crf (23) and H265Crf (28). Two-pass ABR is offered only for an explicit target file size, since that is the one case it wins.
  • Progress comes from parsing out_time_us, frame and speed off pipe:1, against the probed duration. This gives a real percentage and a real ETA rather than a spinner.
  • Hardware encoding reads EncodingOptions.HardwareAccelerationType and the VAAPI/QSV device. Opt-in, clearly labelled: much faster, meaningfully worse quality per bit than a CPU encode at the same size. Note that AllowHevcEncoding and AllowAv1Encoding both default to false server-side — the plugin should surface that rather than silently failing.
  • Preservation is explicit: chapters, metadata, stream languages and dispositions, subtitles and font attachments all carried over by default. Silently dropping a user's fonts is a bug report waiting to happen.

HDR, honestly

SourceThrough an FFmpeg re-encode
SDRFine. Nothing to preserve.
HLGSurvives on colour tags alone.
HDR10Only if mastering-display and MaxCLL/MaxFALL are re-injected via -x265-params and the colour tags are set explicitly. Read them from the source probe and pass them through — otherwise output plays washed-out. x265 is the reliable path here; AV1 encoders are weaker at it.
HDR10+Dynamic metadata needs a build with HDR10+ support and a JSON extract/inject round trip. Treat as out of scope for v1; warn that it degrades to base HDR10.
Dolby VisionThe RPU does not survive. FFmpeg can parse DV metadata but cannot re-inject it on encode; that requires dovi_tool and a raw x265 pipeline. Profile 5 content re-encoded this way plays with badly wrong colour on DV displays.
Hard blockWhen VideoRangeType is DOVI, the planner refuses any video re-encode by default. It offers exactly two paths: keep the video stream untouched and optimise audio/streams only, or an explicit, separately-confirmed "convert to HDR10 and discard Dolby Vision". No silent degradation.

Estimating output size

CRF has no knowable output size in advance, which makes naive estimates useless. Two tiers: a heuristic table keyed on codec, resolution and CRF, displayed as a range with a stated ±25%; and an opt-in sample probe that encodes three 15-second segments taken from 25/50/75% of the runtime with the real settings, measures actual bitrate, and extrapolates. The probe costs about a minute and turns a guess into a defensible number.

07Lossless

Lossless mode, honestly

Yes, a genuine lossless mode is possible — but almost none of its savings come from the video stream, and the single most common expectation about it is wrong. Getting this right in the UI is the difference between a trustworthy tool and one that quietly destroys libraries.

The core misconceptionYou cannot losslessly re-compress an already-lossy video stream. Encoding an existing H.264/H.265 file with -qp 0 or to FFV1 preserves the decoded pixels, and decoded pixels carry far more entropy than the compressed bitstream they came from. The result is typically 3–20× larger than the input. No tool avoids this; it is information theory, not a missing feature. The plugin should not offer this option at all for lossy sources — offering it and letting the user discover the 40 GB output is a design failure.

What genuinely does reduce size with bit-exact output:

TechniqueBit-exactTypical savingWhen it actually helps
Drop unwanted streams
stream selection via -map		 yes10–50% The big one. Remuxes routinely carry a 3–6 GB TrueHD 7.1 track, a commentary track, and five dubs. Keeping two tracks instead of eight is a huge, zero-quality-cost win on the streams you keep.
Lossless audio → FLAC
TrueHD · DTS-HD MA · LPCM		 yes10–35%
50%+ from LPCM		 FFmpeg decodes TrueHD and DTS-HD MA losslessly, so FLAC re-encoding is bit-exact on the PCM. Real savings, especially from LPCM Blu-ray rips.
Strip filler NAL units
-bsf:v filter_units		 yes0%, or 10–20% All-or-nothing. Broadcast captures and some camera output pad to constant bitrate with filler data; removing it is free. On a normal encode there is no filler and this does nothing.

-c copy		 yes< 1% Effectively never a size strategy — container overhead is noise. Worth doing for compatibility and +faststart, but the UI must not sell it as compression.
Lossless video re-encode

only from a lossless source		 Only unlocked when the source video codec is itself lossless or uncompressed — FFV1, HuffYUV, MagicYUV, v210, rawvideo. Genuinely excellent for camera and archival material; irrelevant to a normal movie library. Gate it on a detected source codec, greyed out with an explanation otherwise.
Drop attachments & cover art yes< 1% Marginal. Listed for completeness, and because embedded fonts matter for ASS subtitles — dropping them is a visible regression, not free.
Audio caveatsFLAC has no object-audio container, so converting a TrueHD Atmos or DTS:X track keeps the lossless channel bed and discards the height objects. The audio is bit-exact for the bed and unquestionably a downgrade for anyone with an Atmos setup. Label it that way. FLAC also caps at 8 channels, and FLAC-in-MP4 has poor client support — steer these conversions to Matroska.
Provable, not assertedBecause the lossless claim is falsifiable, prove it. After a lossless-mode job, hash the decoded output of each retained stream on both files and compare:
ffmpeg -i FILE -map 0:a:0 -f hash -hash md5 -
Matching hashes are displayed in the job result as a verification badge. Any mismatch fails the job and leaves the original in place. This is a small amount of work and it is the feature's main credibility.

What the UI must say

Three clearly separated tiers, never blurred:

  • Lossless — output decodes bit-identically. Only the techniques above. Hash-verified.
  • Visually lossless — CRF 16–18. Looks the same to most people at normal viewing distance. It is still lossy, still accumulates generation loss on repeat passes, and must never be labelled lossless.
  • Lossy — everything else, with the estimated saving shown up front.
08Queue

Queue and background processing

A BackgroundService draining a persisted queue, with a default concurrency of 1. Jobs live in SQLite under Plugin.Instance.DataFolderPath, so a server restart mid-encode is recoverable: anything left in Running at startup is marked Interrupted, its temp file deleted, and it is either requeued or surfaced for the user to decide.

Job lifecycle

Queued → Probing → Encoding → Verifying → Applying → Completed
                       ↓           ↓          ↓
                   Cancelled    Failed    Failed (original untouched)
  • Cancellation propagates a CancellationToken to the runner, which kills the FFmpeg process tree and removes the temp file. Cancelling is always safe because nothing has touched the original yet.
  • Progress is polled by the dialog at 1–2 s. SSE is a nice-to-have; polling is the version that reliably survives reverse proxies.
  • Scheduled task (IScheduledTask, visible in the dashboard) handles quarantine expiry, orphaned temp cleanup, and optional bulk sweeps over a library against a saved profile.
Resource contention — a real limitationJellyfin exposes no resource governor to plugins. A four-hour AV1 encode competes directly with live transcoding sessions, and nothing in the API will arbitrate. The available mitigations are all crude: keep concurrency at 1 by default, drop the process priority via ProcessPriorityClass, cap -threads below core count, and offer "pause the queue while anyone is watching" backed by ISessionManager. Be upfront in the plugin description that heavy encoding on the same box as playback will be felt.
09Safety

File handling and safety

This is the part that decides whether the plugin is trustworthy. The governing rule: the original file is not touched until a verified replacement exists on disk.

Preflight, before a single frame is encoded

  • Free space on the temp volume ≥ estimated output × 1.5
  • Source mtime stable over a configurable window — never grab an in-progress download
  • No active playback session on this item (ISessionManager)
  • Target directory writable; skip if the library is on a read-only mount
  • Item is a plain single file — exclude ISO, BDMV/VIDEO_TS folder rips, .strm, and multi-part stacked versions

The verification gate

  • Output non-zero and ffprobe-parseable
  • Duration within ±0.5% or ±1 s of source
  • Expected stream count and types present
  • Full decode scan (-v error -f null -) for corruption — optional, doubles the job time, on by default for replace policy
  • For lossless mode, matching per-stream decoded hashes

Output policies

PolicyBehaviourRisk
Sidecar (default)Writes to a separate directory. Original never modified.none
Alternate versionLinks the new file to the same item via LinkedAlternateVersions, so both appear under one entry and the user picks at playback.low — uses more disk, not less
ReplaceAtomic move into place, original moved to a quarantine folder with a retention period, deleted only after it expires. Revert available until then.destructive — admin-only, explicit confirm

Library reconciliation after a replace

Easy to get catastrophically wrongIf the container changes, the file extension changes, so the path changes. Update BaseItem.Path and call ILibraryManager.UpdateItemAsync on the existing item — never let a rescan create a new one. Watched state, playback position, favourites, playlist and collection membership, and user ratings are all keyed on the item's Id. Letting the old item be removed and a new one created silently wipes every one of those, across every user on the server, with no undo. Also rename .nfo, artwork and external subtitle sidecars alongside; call ILibraryMonitor.ReportFileSystemChanged so the watcher does not race the swap; and invalidate trickplay tiles and chapter images, which are now stale.

Atomicity

Prefer File.Move within one filesystem. If temp and library are on different volumes — common in Docker — that is a copy, not an atomic rename, so copy to a hidden sibling file in the target directory first, flush, then rename within the directory. Never leave a window where neither file is complete.

11Delivery

Build and delivery phases

Ordered so that something honest and useful exists early, and every destructive capability arrives only after the machinery that makes it safe.

M0
SkeletonProject targeting net8.0, Jellyfin.Controller 10.11.x with <ExcludeAssets>runtime</ExcludeAssets>, plugin GUID, config class, dashboard page, build.yaml + jprm packaging, GitHub Actions release into a manifest repo.
M1
Analysis, read-onlyProbe service, /Analyze and /Capabilities. Injection pipeline and the info dialog. Ships as a genuinely useful "what is this file" tool with zero risk attached — and proves the fragile layer works before anything depends on it.
M2
Encoding corePlanner, runner with progress, job store, background worker, verification gate. Sidecar output only. Presets and custom options wired to the dialog.
M3
Lossless modeStream selection, lossless-audio detection and FLAC path, filler stripping, source-codec gating for lossless video, hash verification badge.
M4

M5
PolishSample-probe estimates, hardware encoder support, saved profiles, bulk sweep task, HDR10 metadata pass-through, per-item optimisation history.
Open decisions for you
  • Take a hard dependency on File Transformation, or ship the on-disk fallback too? The fallback widens compatibility and adds the plugin's only real footgun.
  • Is replace-in-place in scope at all for v1, or is sidecar plus alternate-version enough? Dropping it removes most of the catastrophic risk surface.
  • Should non-admin users see the analysis dialog read-only, or nothing at all?
  • Which Jellyfin versions to support — 10.11.x only is much cheaper than 10.10 + 10.11 given the DOM churn.
